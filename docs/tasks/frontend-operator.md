# Frontend: operator dashboard

The dashboard of the transport operator is the centre of the demo. It shows the live network, predictions with confidence, alerts, and the demo control panel.

- **May edit:** `frontend/` (except `frontend/src/citizen/`), `scripts/dev.ps1`.
- **Must not:**
  - edit `frontend/src/api/generated.ts` by hand (run `./scripts/gen-types.ps1`);
  - call `fetch` outside `src/api`.

### UI rules

- Every value shows its `kind` (observed, predicted, simulated) and its age.
- Unavailable values read "unavailable", never 0.
- Levels use colour **and** text.
- A permanent banner says "Simulated data: bus movements and counts are generated by a simulator". In mock mode it also says "Mock data".
- Controls are keyboard accessible, with visible focus and labels.

## O1 - Skeleton, API adapter and generated types

- **Priority:** P0
- **Status:** todo
- **Depends on:** C1 (and the alignment decision above)

### Objective

A running Vite app with a typed API adapter that switches between mocks and the live backend.

### Instructions

1. Vite + React + TypeScript (strict) in `frontend/`, with the stack of AGENTS.md pinned in `package.json`, `openapi-typescript` as a dev dependency, and `package-lock.json` committed.
   - `npm test` runs Vitest in run mode (`vitest run`).
2. Entry:
   - `src/main.tsx` renders the operator dashboard;
   - `?app=citizen` renders the citizen placeholder (`src/citizen/`, owned by the citizen tasks).
   - No router library is needed.
3. `src/api/`:
   - `generated.ts` from `./scripts/gen-types.ps1`;
   - `adapter.ts`: an `Api` interface with one method per endpoint used by the dashboard;
   - `mock.ts`: fixtures built from the SPEC example payloads, typed with the generated types;
   - `live.ts`: base URL from `VITE_API_BASE`, default `http://127.0.0.1:8000`;
   - `ws.ts`: WebSocket client for `/ws/live` with reconnect and parsing of `WsEnvelope`. In mock mode, a fake emitter sends clock and vehicle deltas;
   - TanStack Query hooks (`useStops`, `useVehicles`, `useAlerts`, ...) that merge WS deltas into the query cache.
   `VITE_API_MODE=mock|live` selects the implementation.
4. Shared components:
   - `ValueBadge` (kind + age);
   - `LevelBadge` (colour + text);
   - `Unavailable`;
   - the `SimulatedBanner`.
5. `scripts/dev.ps1` opens two PowerShell windows: the backend (`uv run uvicorn app.main:app --host 127.0.0.1 --port 8000` in `backend/`) and the frontend (`npm run dev` in `frontend/`).

### Tests

- The mock adapter returns data that matches the generated types (compile-time check + one runtime test).
- The banner is always rendered.
- `ValueBadge` renders "unavailable" for an `UnavailableValue`.
- `LevelBadge` renders the level text.
- The WS client parses each envelope type.

### Acceptance

```powershell
cd frontend
npm ci
npm test            # green
npx tsc --noEmit    # no type errors
```

Manual: `npm run dev` with `VITE_API_MODE=mock` shows the empty dashboard layout with the banner.

The dashboard shell runs on mocks, before the backend exists.

## O3 - Demo control panel

- **Priority:** P0
- **Status:** todo
- **Depends on:** O1, S3. The camera switch needs S5.

### Objective

Run the whole demo script from the dashboard: clock, scenario, camera switch, and ground truth against prediction.

### Instructions

- Speed buttons x1, x2, x4, x10, x30, x60 (`aria-pressed` on the active one) and a pause/resume toggle → `POST /sim/clock`.
- Scenario selector from `GET /sim/scenarios` → `POST /sim/scenario`.
- Camera switch for the physical camera from `GET /sim/cameras` → `POST /sim/cameras/{camera_id}/mode`.
  - Disabled, with an explanation, when no physical camera is configured.
  - Errors (`409`, timeout) are shown in the panel.
- Truth vs prediction for the selected stop and bus:
  - true waiting (by line) and true onboard from `/sim/truth`, labelled **simulated ground truth**;
  - next to them, observed and predicted values.
- The last display payload of the physical stop (`last_display` from `/sim/cameras`) as a preview of what the Arduino shows.

### Tests

- Clicking x10 calls `POST /sim/clock` with `{speed: 10}`.
- Pause sends `{paused: true}`.
- Scenario change calls the API.
- A `409` on the camera switch shows an error message.
- Truth values carry the "simulated" label.

### Acceptance


## O4 - Alerts with evidence and acknowledgement

- **Priority:** P0
- **Status:** todo
- **Depends on:** O1, K4

### Objective

The operator sees what needs attention first, why, and can take ownership of it.

### Instructions

- List from `GET /api/operator/alerts`, sorted by severity then age, filterable by state and severity, updated by WS `alerts`.
- Each item shows:
  - type, stop, line, trip and state;
  - age in sim time;
  - evidence values with `ValueBadge` (observed or predicted);
  - for POSSIBLE_ABANDONMENT, an "inference" tag.
- Acknowledge button → `POST /api/operator/alerts/{alert_id}/ack`. `409` → refresh and show "already resolved".
- New high-severity alerts are announced in an `aria-live="polite"` region.
- Selecting an alert highlights its stop or bus on the map.

### Tests

- Sorting.
- The ack call.
- `409` handling.
- Evidence labels.
- The live region updates on a new high alert.

## O5 - Stop and bus detail

- **Priority:** P0
- **Status:** todo
- **Depends on:** O1, K3

### Objective

The detail behind every coloured dot on the map.

### Instructions

- **Stop panel** (`/api/stops/{stop_id}`):
  - observed waiting with source (simulated or physical) and age;
  - passer-by estimate;
  - camera mode and status;
  - next buses with ETA, predicted onboard at departure, interval_80, level, confidence in %, may_not_fit, and stop level per line.
- **Bus panel** (`/api/vehicles/{vehicle_id}`):
  - observed onboard and seated/total capacity;
  - delay;
  - a row per downstream stop with ETA, predicted onboard, interval_80, level and confidence.
- Live updates from WS `predictions`. Stale values show "unavailable".

### Tests

- Renders the SPEC `GET /api/stops/{stop_id}` example: 75, [70, 79], yellow, 69%.
- A stale waiting value shows "unavailable".
- `may_not_fit` shows a text warning.

## O6 - History, insights and calibration chart

- **Priority:** P1
- **Status:** todo
- **Depends on:** O1, K6

### Objective

Operator analytics on system flaws, and visible proof that the confidence is calibrated.

### Instructions

- **History** (`/api/operator/history`): mean and peak occupancy and waiting by stop, line and time of day, with a comparison across days (Recharts).
- **Insights** (`/api/operator/insights`):
  - lost demand ranking with estimated lost fares;
  - chronic overcrowding;
  - bunching;
  - APC drift;
  - camera reliability.
- **Calibration** (`/api/operator/calibration`):
  - reliability diagram with the diagonal and a ±10 point band;
  - bucket counts;
  - buckets with fewer than 30 predictions greyed out.
- Charts have a text table alternative.

### Tests

- Each view renders its mock data.
- The calibration chart shows the band.
- The table alternative exists.
